# Database contract and migrations

Dedicated restaurant project only. The local runner uses a separate cluster at 127.0.0.1:55434/database `cestdelicieux_test`, synthetic Auth fixtures and no remote DSN. It resets only those disposable schemas. Hosted migrations never contain Auth fixture definitions.

Generated by Supabase CLI 2.120.0:

1. `20261011151015_restaurant_foundation.sql` — tables, explicit grants/RLS, profile trigger, service-only delivery reservation/storage and atomic request throttling.
2. `20261011151444_transactional_orders.sql` — atomic current-price checkout, owner/request/payload-bound replay, quote consumption, recovery tombstones and immutable order snapshots.
3. `20261011152046_staff_contact_apis.sql` — authenticated staff status/payment/catalogue/settings/inbox APIs, version checks and action replay, confirmed customer contact submission.

Run `seed.sql` after all three. The setup bundle combines these in the same order; it does not contain local Auth fixtures. Hosted migrations were run manually by the owner. Local integration tests cover all three against PostgreSQL; hosted permissions/advisors need the dedicated account.

Public JSON APIs return `{ok:true,data}` or `{ok:false,code,message}`. Public wrappers are SECURITY INVOKER; privileged private implementations explicitly validate identity/membership. Default PUBLIC function execution is revoked. No browser table writes to orders, quotes, membership or audit. Price/routing secrets never come from the browser.
